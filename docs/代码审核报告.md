# PDF 工具箱 — 代码审核报告

> 审核日期：2026-11-11 · 版本：1.0.0 · 范围：前端（原生 JS + Vite + PDF.js）、Rust 后端（Tauri 2 + lopdf）、打包配置
> 结论：项目完成度高、架构清晰、文档与代码基本同步；但存在 **1 个确定的功能 Bug**、**1 条安全可利用链** 和 **1 个健壮性崩溃点**，建议发布前优先处理。

> ✅ **修复状态（2026-11-11 更新）**：下列 P0/P1/P2 问题**已全部修复**，并通过 `cargo check`、`cargo test`（含新增加解密往返/中文解码单测）、`npm run build` 验证。逐项对照见文末「修复对照表」。验证记录与遗留风险（未签名、需真机冒烟）亦见文末。

## 总体评价

- ✅ 模块划分清晰，前后端职责分明，公共能力已抽离（`common.js` / `pdf_util.rs`）。
- ✅ Office 转换、Shell 调用使用**参数化传参 + 环境变量**，无命令注入风险；这是同类项目常见坑，这里处理得很好。
- ✅ capabilities 权限克制（仅窗口控制 + 对话框），未开放宽泛 fs scope。
- ✅ 编码 UTF-8 BOM、超时缓存、资源释放（Office COM）等细节有考虑。
- ⚠️ 但 **安全边界（CSP / 文件读写命令）**、**耗时任务不阻塞 UI**、**加解密正确性** 三块需要系统性补强。

## P0 — 发布前必须修复

### P0-1【功能 Bug，已证实】解密 PDF 必然失败
**位置**：`src-tauri/src/security.rs:172-173`

```rust
let mut doc = load_document_with_password(source_path, &password)?; // 已解密，is_encrypted()=false
decrypt_document(&mut doc, &password)?;                              // → 命中 "PDF 未加密" 错误
```

`decrypt_document` 开头有 `if !doc.is_encrypted() { return Err("PDF 未加密") }`。根据 lopdf 0.39 语义，`load_with_password` 用**正确密码**加载后，对象已在内存中解密，`is_encrypted()` 返回 `false`。因此第二行**必然返回错误**，解密功能对正确密码也会报"PDF 未加密"或走不到保存。

- 同模块的 `prepare_doc`（info.rs:62）、`clear_pdf_metadata`（security.rs:187）、`redact` 采用的是"先 `is_encrypted()` 判断再解密"的**带守卫**模式，逻辑上可跳过重复解密，**本身无此 Bug**——但同样建议补集成测试确认保存后输出为明文（trailer 的 `/Encrypt` 是否被清除）。
- **建议**：`decrypt_pdf` 改为二选一——(a) `load_document` 加载 → 显式 `decrypt_document`（去掉那次 `load_with_password`）；或 (b) 仅 `load_with_password`，删除第二次解密调用。用真实加密样例（空 owner 密码 / 错误密码 / 正确密码）补 3 个集成测试。

### P0-2【安全，可利用链】XSS → 任意本地文件读写
**位置链**：
1. `tauri.conf.json:29` `"csp": null` —— 完全禁用内容安全策略；
2. `tauri.conf.json:13` `"withGlobalTauri": true` —— 页面可直接拿到 `window.__TAURI__`；
3. `js/tools/security.js:18-31` `showMeta()` 把 PDF 元数据 `title/author/...` **未经转义**拼进 `innerHTML`；
4. `src-tauri/src/info.rs:99-105 / 122-130` `read_pdf_file` / `write_binary_file` 接受**任意路径**，无任何白名单或目录边界校验，后者还会 `create_dir_all`。

攻击者只需构造一个标题含 `<img src=x onerror="...invoke('write_binary_file',...)">` 的恶意 PDF，用户点"查看元数据"即触发脚本，进而可**读写/覆盖本机任意文件**。自定义 command 不受 capability 白名单约束，这条链风险很高。

**建议**（按性价比排序）：
1. 在 `common.js` 增加 `escapeHtml()`，把所有拼进 `innerHTML` 的动态片段（元数据、文件名、后端错误字符串）统一转义；`showMeta` 优先改用 `textContent` + `createElement`。同类注入点：`watermark.js:37-39`（字体 label/path）、`compress.js:38,62`、`scan.js:34,58`、`pages.js:90,137`、`convert.js:138,145`。
2. 设置严格 CSP（需按 PDF.js worker 加载方式实测）：
   `"default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' asset: http://asset.localhost data: blob:; font-src 'self' data:; connect-src 'self' ipc: http://ipc.localhost"`
3. 生产构建 `withGlobalTauri: false`，统一用 `import { invoke, dialog } from '@tauri-apps/api/...'`（当前 `common.js:4` 仍用 `window.__TAURI__.dialog`）。
4. 给 `read_pdf_file` / `write_binary_file` 增加路径边界校验（规范化后必须落在用户通过 dialog 选定的目录内）、扩展名与大小上限；长期应改用 Tauri `asset` 协议替代字节穿桥。

### P0-3【健壮性，可崩溃】页码范围展开无上界导致 OOM
**位置**：`src-tauri/src/pdf_util.rs:31-33`（越界检查在 49-53 行，**在展开之后**）

`"1-4294967295"` 会在校验 `p > max_page` 之前先生成数十亿个 `u32`，瞬间吃满内存并崩溃。该函数被提取/删除/旋转/裁剪/拆分/水印等大量命令复用，攻击面大。

**建议**：把边界校验提到展开之前：
```rust
if start == 0 || end == 0 || start > end || end > max_page { return Err(...); }
// 再做 start..=end；并对单次展开数量设上限
```

## P1 — 尽快处理

| 编号 | 位置 | 问题 | 建议 |
|---|---|---|---|
| P1-1 | `compress.rs` / `scan.rs` / `pages.rs` / `convert.rs` / `watermark.rs` / `fonts.rs:398` | 除 Office 外**所有耗时命令都是同步** `#[tauri::command]`，在主线程运行，大文件/大批量时 UI 冻结；`list_system_fonts` 递归解析系统字体可能卡数秒 | 统一改为 `async fn` + `spawn_blocking` 包裹；字体列表做进程内缓存 |
| P1-2 | `info.js:124`、`redact.js:153`、`convert.js:186,240` | PDF.js `getDocument()` 后从不 `destroy()`，批量导出几十个 PDF 持续占内存；canvas 未归零、`page.cleanup()` 未调用 | 切换前 `await pdfDoc.destroy()`；导出用 `try/finally` 释放；渲染后 `page.cleanup()` |
| P1-3 | `common.js:305-326` | 每个工具模块 init 都注册一次**窗口级** `onDragDropEvent`，8 个模块共 8 个全局监听且不取消；在压缩页拖入文件会触发已访问模块的表单回调，造成串扰 | 窗口级拖放只在 `app.js` 注册一次，按当前 active 视图分发；保存 `unlisten` |
| P1-4 | `pdf_util.rs:6-9` + 各命令 | `save_document` 直接 `File::create(out)` 截断；未校验 `output_path != source_path`，误操作可覆盖源文件 | 统一入口比较 `canonicalize` 后的源/目标路径；改"临时文件 + 原子 rename" |
| P1-5 | `common.js:36-44` | 默认输出为同目录 `原名-后缀.pdf`，用户不改路径直接执行会**静默覆盖**已存在的同名文件 | 执行前检测存在并确认，或生成 `...(2).pdf`，或 UI 明示"将覆盖" |
| P1-6 | `security.rs:48-54` | 加密使用 `EncryptionVersion::V2` + `key_length:128`，即 **RC4-128**，已被 PDF 2.0 弃用且有弱点 | 改用 AES-128（V4/R4）或 AES-256（V5/R6），视 lopdf 0.39 支持情况 |
| P1-7 | `security.rs:152-154` | owner 密码留空时回退为 user 密码，导致"打开密码"="所有者密码"，打印/复制权限限制形同虚设 | 强制单独设置 owner 密码，或明确提示"留空则权限限制不生效" |
| P1-8 | `security.rs:74-94` | "清除元数据"只删 `/Info` 字典，**未处理 Catalog 的 `/Metadata`（XMP）流**，隐私信息仍可能被提取 | 同时移除 `/Metadata` 引用及 XMP 流、`/PieceInfo`，并做重载自检 |
| P1-9 | `security.rs:103-110` / `convert.rs:134-138,237` | 中文支持不足：元数据只 `from_utf8_lossy`（不识别 `FE FF` UTF-16BE）；文本转 PDF 用无中文字形的 Courier；`read_to_string` 遇到 GBK 编码 txt 直接报错 | 元数据按 BOM 解码；文本 PDF 复用 `fonts.rs` 的 TrueType 子集嵌入；txt 读取做 UTF-8→GBK 回退 |
| P1-10 | `index.html:823` | 文案"配合清除元数据即可彻底清除底层文字"**具有安全误导**——清文档属性不会删除页面内容流中的真实文字 | 改为"叠加遮盖不删除底层文字；真正不可恢复需内容擦除（redaction），分发前请核验输出"；与后端 `apply_pdf_redaction` 实际能力对齐 |
| P1-11 | `compress.rs:80` / `scan.rs:223`（批量） | 批量任务串行且无进度上报，`progress.rs` 的 `task-progress` 事件只有 Office 用 | 批量逐项 `emit_progress(i/total)`，前端遮罩显示进度；配合 P1-1 放入后台线程 |

## 建议修复顺序

1. **第 1 批（功能 + 安全）**：P0-1 解密 → P0-2 转义 + CSP + 路径校验 → P0-3 页码边界。
2. **第 2 批（稳定性）**：P1-1/P1-2/P1-3 主线程、内存、拖放串扰 → P1-4/P1-5 覆盖防护 → 补 P0-1 的集成测试。
3. **第 3 批（正确性与体验）**：P1-6~P1-11 加密/元数据/中文/文案/进度 → P2 逐项清理。
4. 发布前补：`LICENSE`、真实加密 PDF 与中文 txt 的回归用例、`npm run tauri build` 冒烟。

> 打包补充：`tauri.conf.json` 的 `bundle.targets` 仅 `nsis`，且 `certificateThumbprint: null`（未签名），Windows 下会触发 SmartScreen 警告；如需分发建议补 MSI 目标与代码签名。

### 反杀毒误报加固（2026-11-11 补充，零成本）
未签名 Tauri+NSIS 程序是 Windows Defender / 第三方杀软启发式误报的高发区（`Trojan:Win32/...!ml`、`Win32:NSIS_Error[Heur]` 等）。已做以下**不花钱**加固降低被误判概率（无法 100% 根除，根治仍靠代码签名）：

| 措施 | 改动 | 作用 | 状态 |
|---|---|---|---|
| 版本信息厂商 | `tauri.conf.json` 加 `bundle.publisher: inkdot` | VERSIONINFO 的 `CompanyName` 由默认 "pdf" 改为 "inkdot"，与版权一致，摆脱匿名感 | ✅ 保留 |
| NSIS 安装模式 | `installMode: perMachine` → `currentUser` | 装到用户目录、免 UAC、写入行为更轻；尚未分发，无存量迁移成本 | ✅ 保留 |
| ~~完整 Windows 应用清单~~ | ~~`app.manifest` + `WindowsAttributes::app_manifest()` 注入~~ | ~~asInvoker / supportedOS / DPI~~ | ❌ **已回退**（见下） |

**已实测核验**：`pdf-compress.exe` 的 `CompanyName=inkdot`、`LegalCopyright=Copyright © inkdot` 生效。`cargo check`、`npm run tauri build` 通过并产出安装包。

**⚠️ 重要教训——自定义 manifest 注入已回退**：曾按"加固"思路新增 `app.manifest` 并用 `build.rs` 的 `WindowsAttributes::app_manifest()` 注入（含 asInvoker/supportedOS/DPI/longPathAware）。实测发现**该 exe 启动即崩 `0xC0000139 STATUS_ENTRYPOINT_NOT_FOUND`**（进程句柄=0、内存仅 4MB）。对照实验（默认清单 vs 完整清单 vs 精简清单，仅 manifest 变量不同）证实：默认清单版正常启动（窗口句柄正常、34MB 稳定），两种注入版均异常。判定为自定义清单在此工具链下的资源/加载回归——反误报收益是"概率性"的，却带来 100% 启动失败风险，故**回退 `build.rs` 至 `tauri_build::build()`、删除 `app.manifest`**。**结论：不要为了反误报手动注入 Windows manifest；厂商名（`publisher`）与安装模式（`currentUser`）这两项零风险加固已足够提供身份信息。**

**「被警告」与「被删除」是两个不同子系统，务必分清**：
- **SmartScreen（信誉层）**：提示「Windows 已保护你的电脑」，可点「更多信息 → 仍要运行」，**不删除文件**。无代码签名的新文件信誉为零时会触发，随下载量增长消失。
- **Defender 防病毒（查杀层）**：报出具体威胁名（如 `Trojan:Win32/…!ml`）会**直接隔离/删除，无「仍要运行」选项**。这才是真正「被删」的情形，几乎都是启发式误报。
- 本工具不下载/释放/执行额外程序（区别于那些被卡巴斯基查杀的「现场编译/下载模型」类应用），行为面干净，已是降低误报的最大有利因素。

**若真被 Defender 误报——官方申诉（通常 1–2 天全局清除）**：
1. 打开 Windows 安全中心 → 病毒和威胁防护 → 保护历史记录，记下完整威胁名（如 `Trojan:Win32/Foo!ml`）、检测时间。
2. 从 CI/本机重新构建一份**与发布完全相同**的文件（重新编译哈希会变，勿用被隔离件），到 https://www.microsoft.com/wdsi/filesubmission 提交。
3. 登录，角色选 **Software developer**，"是否含恶意软件" 选 **No**，附注写清威胁名、security intelligence 版本、文件来源（合法桌面工具、当前未签名）。可用 `https://www.microsoft.com/wdsi/submissionhistory` 跟踪。
4. 判定误报后更新 Defender 安全智能（检查更新）即可解除；该修正对所有人全局生效。切勿为图省事关掉实时防护或给整个下载目录加排除。

### 遗留风险 / 需真机确认
1. **未签名（无法靠配置根除）**：`certificateThumbprint:null`。上方已做零成本加固降低误报概率，但只要未签名，SmartScreen 首次警告与 Defender 启发式误报的**可能性仍无法归零**——唯一根治是可信 CA 签名。尚未分发可先发；正式分发方案见文末「代码签名方案」。

## 代码签名方案（2026-11 调研，尚未分发）

**结论：签名基本都要花钱，但有免费路径；且 EV 已不再「秒过」SmartScreen，别为消警告多花冤枉钱。**

| 途径 | 2026 参考价 | 说明 |
|---|---|---|
| 自签名（OpenSSL 自制） | 免费 | **无效**：仍显示「未知发布者」+ SmartScreen 红框，甚至被 Defender 查杀。仅供本地/企业内测，不适合公开发布。 |
| Azure Trusted Signing（原 Artifact Signing，微软托管） | 约 $9.99/月（Basic，5000 次签名/月）| 目前**最便宜的正规**方案；需美/加地区资格（个人）或欧盟/英国组织。国内个人通常不满足。 |
| SSL.com OV | $129/年（5 年期约 $96.75/年）| 支持个人身份验证（IV）+ 纯云签名 eSigner，无需邮寄 UKey；个人开发者较现实的正规选择。 |
| Certum OV（国内代理商） | 约 ¥1200/年 | 云签名免硬件，1–3 天签发，微软根信任，国人购买/开票方便。 |
| Sectigo OV / EV | OV 约 $220/年、EV 约 $285/年 | — |
| DigiCert OV / EV | OV $696/年、EV $972/年 | 大牌，兼容性/售后最强，价格最高。 |
| **SignPath Foundation（开源项目）** | **免费** | 符合条件的**开源项目**可免费获得 OV 级托管签名。若本项目开源，这是首选。 |
| **Microsoft Store 分发 MSIX** | **免费** | 商店自动代签，用户永不见 SmartScreen；但仅限 MSIX 且须上架商店（商店开发者账号免费）。 |

**关键事实纠正（很多人不知道）**：微软在 **2024 年 8 月**更新 Trusted Root Program，**取消了 EV 证书的 SmartScreen 即时信誉直通**。现在 OV 与 EV 在 SmartScreen 上表现一致——新软件都要靠下载量+干净运行记录逐步积累信誉。因此「花 $400+/年买 EV 只为跳过首次警告」已不成立；EV 现在主要价值是签 Windows 内核驱动、WHQL 认证、企业采购背书。对本项目（普通桌面工具、非驱动）**OV 足够**。

**给本项目的建议**：尚未分发，可先不签、直接发（用户会看到一次 SmartScreen 警告，点「更多信息→仍要运行」即可）。等确定分发方式后：① 若走开源 → 申请 SignPath 免费签名；② 若官网直发且愿付费 → Certum OV（¥1200/年，国内最省心）或 SSL.com OV（个人可办、云签名）；③ 若要最顺滑体验 → 上架 Microsoft Store（MSIX 免费代签）。签名时务必加 RFC3161 时间戳，证书过期后旧版本签名仍有效。要配置签名流水线（`signtool` + `tauri.conf.json` 的 `certificateThumbprint`）可随时让我接上。

#### 开源变现 × 免费签名的冲突（2026-11 补充）
用户设想「开源 + 软件免费 + 电商卖下载链接 + 用 SignPath 免费签名」。结论：**法律可行，但免费签名与「卖二进制」在多数卖法下互斥**。

- **法律层**：开源不等于不能收费。MIT 明确授予 use/copy/modify/distribute/**sell copies** 的权利，唯一义务是保留版权与许可声明（国内《著作权法》同样要求遵守开源协议、保留声明）。所以"开源软件收费"本身合法。
- **SignPath 条款硬约束（引自 signpath.org/terms.html）**：① 必须 `OSI-approved license without commercial dual-licensing`（**禁止商业双授权**）；② `No proprietary code`（**禁止任何专有/非开源组件**，尤其维护者自己发布的）；③ 签名二进制 `must be a valid, automated build resulting from the source code`（**必须与其公开仓库源码可验证构建一致**）；④ 证书 `issued to SignPath Foundation`，**发布者显示 SignPath Foundation 而非你本人**；⑤ 每次发布需人工审批、全员 MFA、项目主页写 "Code signing policy"；⑥ 官方 `under no obligation to accept your project`（可自由拒绝）；条款仍标注 Draft。
- **结构性矛盾**：正因为③，SignPath 签的那份二进制，任何人都能从你的公开仓库免费编译/下载 → "下载链接"本身没有稀缺性，卖点消失；若想造稀缺性（付费专业版 / 闭源增值），则直接违反①②，同份二进制也无法用 SignPath 签。且④意味着签名并不给你的品牌背书。
- **可行路径**：A 卖服务不卖二进制（一键包/文档/答疑/定制）——可用免费签名；B open-core 专业版——违反条款，须自购 OV 证书（≈¥1200/年）；C 纯赞助（Sponsors/爱发电）——可用免费签名。
- **电商合规（国内）**：不要「宣称永久免费」却又收费（涉虚假宣传/《广告法》《消保法》）；虚拟商品宜包装为「授权许可 + EULA」、邮箱发货、用网盘链接避免自建站触发 ICP 备案；避免个人微信/支付宝长期收款（账户冻结风险）；按营收申报（<5 万个人经营所得，5–50 万建议个体户）。

### CI 首跑发现并修复的跨平台 Bug
- **macOS job 构建失败（E0425）**：首次 tag 触发 CI（run `42940719616`）时 Windows job 成功，macOS job 在「构建 Tauri」步骤失败。日志定位：`office.rs` 的 `OfficeKind::body()` 在所有平台编译，但引用的 `WORD_BODY`/`EXCEL_BODY`/`PPT_BODY` 三个 PowerShell COM 脚本常量仅在 `#[cfg(windows)]` 下定义 → macOS 上 `cannot find value WORD_BODY/EXCEL_BODY/PPT_BODY in this scope`。Windows 本地编译正常故此前未暴露。
- **修复（提交 `1d0bc67`）**：将 `body()` 及 Windows-only 的 `OfficeKind` 枚举、`app_name/prog_id`、`kind_from_path`、Office 缓存结构/`OFFICE_CACHE`/`CACHE_TTL`、`emit_progress`/`Command`/`Output`/`Mutex`/`Duration`/`Instant` 等 import 全部加 `#[cfg(windows)]`；非 Windows 下 `get_office_status` 返回 `platform_supported:false`、`office_to_pdf` 返回「仅支持 Windows」提示。Windows 侧 `cargo check` + `cargo test`（6/6）复验通过。
- **教训**：Tauri 多平台 CI 的价值就在这种地方——Windows-only 功能（注册表、COM、PowerShell）必须用 `#[cfg(windows)]` 从定义到调用整条链隔离，否则交叉平台必挂。仅给常量加 cfg 不够，引用它的方法也要加。
- **本地交叉验证限制**：Windows 机器 `cargo check --target aarch64-apple-darwin` 因缺 macOS C 编译器（`cc-rs` 需 `cc`）无法完成链接前检查，但已确认不再报 E0425；最终以 CI macOS runner 实编为准。
